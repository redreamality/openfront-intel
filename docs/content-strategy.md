# OpenFront Intel 内容战略

更新日期：2026-08-20。规划窗口：未来 6–8 周。

本文只回答“为什么做、当前做什么、何时晋级或停止”。实时状态与指标见 [`content-loop.md`](content-loop.md)；Search Console 获取规则见 [`search-console-content-workflow.md`](search-console-content-workflow.md)；`What's New` 的字段与披露合同见 [`whats-new-content-plan.md`](whats-new-content-plan.md)。2026-08-20 前的完整叙事见 [归档](archive/content-strategy-through-2026-08-20.md)，不属于定时任务热上下文。

## 北极星

访问者应在 20 秒内知道：当前版本最影响实战的变化、这一局该怎么做、答案最后何时核验。页面数、字数、PR 数和连续发布天数都不是目标。

主要结果指标：

- 核心答案显示适用版本、核验日期与最重要变化。
- 一个玩家意图只落到一个直接答案页，索引和相邻页负责导流。
- 正式 Release 后 24 小时内有 en + zh 玩家影响摘要，72 小时内同步受影响常青页及 fr/de/nl。
- GSC 中错落地、重复意图和低 CTR 减少；Feedlog、Issues 与社区重复问题最终指向权威答案。

## 稳定原则

1. **先回答玩家决策。** 正文顺序默认是直接答案、版本边界、正确做法与阈值、具体局势、失败与反制、来源和下一步。
2. **先定唯一主答案。** 现有页能完整承接就更新现有页；只有独立意图、成熟证据和自然入口同时成立时才新建页面。多个独立成熟意图可同批交付。
3. **按玩家影响处理版本。** 系列总览负责导航，但小版本或专题有独立决策价值时可以拆页；纯稳定性修复不制造薄页。changelog 只写非 TEST 正式 Release。
4. **事实先于速度。** 正式 Release、上游源码、生成数据或真实反馈至少提供一种可核验证据；`Merged`、`In development`、`Watching` 不能写成已上线。
5. **五语事实一致。** 紧急发布可先 en + zh，但数字、键位、版本范围和结论不能漂移；其余语言必须在 72 小时窗口内补齐并记状态。
6. **不伪造视觉证据。** 无真实截图时使用数据表、HTML/CSS 原生解释图、路线或决策图。
7. **交付单位是玩家结果。** 同一主题的来源、主答案、相邻页、多语、入口、测试和状态收口进入同一个内容 PR；不同风险或可独立合并的主题才拆 PR。

## 触发、晋级与停车

候选进入 Production 必须同时满足：

1. 有明确玩家问题和唯一主落地页。
2. 有正式 Release、源码、生成数据或真实反馈支撑。
3. 新建页时能说明为什么现有页无法完整承接。
4. 有可验证完成定义，而非“增加字数”或“多做一页”。
5. 不依赖未合并前置，不与进行中 PR 争夺同一意图。

优先级依次是：事实错误、正式 Release、当前 Production 的退出条件、有排名基础的答案/入口问题、反复出现但无主答案的玩家问题。用户明确改变口径、事实错误或正式 Release 可立即打断；其他重排只在周/月校准发生。

停车规则：

- 候选输入指纹由上游 Issue/PR SHA、GSC 截止日与查询计数、Feedlog/Issues 状态组成；指纹未变则跳过重复研究。
- 连续三个有效观察窗口没有需求或状态变化，转为 `Parked`，不再占每日 Incubation 检查位；新信号出现时恢复。
- 来源不足、意图重复、依赖未合并、文件冲突或无法完成验证时只暂停该项；其他成熟项可继续。
- 整个候选集都不满足门槛时不创建空 PR、空页面或仅刷新日期的提交。

## 度量与复盘

- 每日：只扫描正式 Release、`What's New` 双锚点增量、已跟踪状态转换和真实新信号；无变化时保留游标，不刷新公共日期。
- 每周：围绕一个玩家结果校准 Production；检查错落地、依赖与退出条件。
- 每月：比较 GSC 7/28 天意图、落地页、CTR、Feedlog/Issues；选择下月主题并记录拒绝原因。
- 每季度：清理过时版本、重复页面和低点击入口；决定地图试点是否继续。

评价 Monitoring 使用稳定窗口与事先写明的门槛，不以单日波动改稿。Water Nukes 的成功基线是主攻略在有效 7 天窗口取得 97 次展现和全部 3 次点击，高于 hotkeys 的 64 次展现；它证明入口和唯一主答案优先于继续复制正文。

## 交付与状态收口

- 自动化可在完整本地验证、最新 `main` 基线、远端 head 一致、PR 可合并、无未解决评论/重叠/依赖后直接 squash merge；不再等待人工审阅。状态不确定或门禁失败时保留 PR 并报告。
- 内容 PR 创建前就在 `content-loop.md` 写入“本 PR 合并即完成/转入 Monitoring/Parked”的目标状态、验证和下一触发点。合并后不再为补完成勾选、merge SHA 或纯运行叙事创建第二个 PR。
- PR 合并状态、SHA、网络重试和无变化扫描只写 automation memory；只有它改变活动通道、公共来源锚点或后续决策时，才随下一个有实质内容的 PR 更新账本。
- 定时任务提示词只保留 Scout / Production / Delivery 阶段接口和自动发布门禁，并指向 `AGENTS.md`、本文件、`content-loop.md` 与当前 Production 计划；不得复制当前候选、运行历史或平台避坑。提示词与三份热文件合计保持小而稳定。

## 明确不做

- 不追求每个单位、建筑、地图或小修复都有页面。
- 不复制 GitHub 活动流、PR 标题列表或 Issue backlog。
- 不把开发中、已合并待发布或不可见依赖写成正式能力。
- 不追逐拼错品牌词，不用无需求内容填满日程。
- 不因五语无法同日完成而延迟紧急 en + zh 事实，也不长期遗忘其余语言。

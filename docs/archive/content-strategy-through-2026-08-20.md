## 北极星：让玩家感到“这里始终是最新的”

访问者应在 20 秒内知道三件事：当前版本最影响实战的变化、自己这一局该怎么做、答案最后何时核验。站点不以总页面数、覆盖所有实体或每日发布量作为增长指标。

优先观察以下结果：

1. 核心攻略是否明确显示适用版本、最后核验日期和本版本最重要的变化。
2. “Water Nukes 怎么用”“什么时候停止扩张”等问题是否落到唯一、直接回答问题的页面，而不是索引页。
3. 正式版本发布后，玩家影响摘要和受影响常青页是否在约定窗口内更新。
4. Search Console 的错落地、低 CTR 和重复意图是否减少。
5. Feedlog、Issues 和社区中重复问题是否被合并为选题并最终指向权威答案。

页面数不是目标，但高价值玩家问题的覆盖深度是目标。当多个独立问题已有可靠来源、清晰意图和可验证完成定义时，应主动扩展多个页面，而不是为了克制页面数把所有答案塞进一篇超长页面，或每次只做一处措辞修补。

## 编辑原则

### 1. 版本内容按玩家影响拆分，不设单页上限

- 版本系列总览可以继续作为导航入口，但不再是该版本系列唯一允许的内容页。
- `vXX.1`、`vXX.2` 等小版本只要带来独立玩家决策、搜索 / 阅读意图或足够完整的正式 Release 内容，就可以建立独立玩家影响页；适合合并时也可以回填总览或常青页。
- 纯稳定性修复、没有独立玩家价值的重复说明仍留在官方 Release 来源中，不为满足数量或频率制造薄页。
- 当前 `v32` 总览已经覆盖 Doomsday Clock、贸易船增长、核弹速度、Defense Post 占领、retaliate、联盟时长、地图工具和 WebGL。后续版本根据实际影响决定合并或拆分，不预设每个版本系列的页面数量。

### 2. 先定主答案，再成组扩展页面

- 能在现有主落地页补直接答案时，不新建页面。
- 新页面必须对应独立的玩家决策；一个搜索意图只能有一个主落地页，但多个已经成熟的独立意图可以在同一执行批次中分别建立页面。
- 不要因为存在一个可做的旧页 quick win，就无限推迟已经具备来源、需求和边界的新攻略。现有页更新与新页面扩展可以并行，只要它们不争夺同一意图。
- 一个批次可以同时新增或深度扩写多篇页面，并同步相关入口、旧页摘要和多语版本；每篇仍必须有自己的直接答案、失败反例、对手反制和完成定义。
- 速查页与教程页可以同时存在，但必须分工：`/shortcuts/` 负责找键，`/guides/hotkeys/` 负责实战工作流和故障恢复。
- Water Nukes 的直接答案必须在 `/guides/water-nukes/` 本文中，索引页只负责导流。

### 3. 从“为什么输了”组织内容

文章先回答局内决策，再给数字、公式和源码依据。默认结构是：

1. 40–80 words 的直接答案。
2. 适用版本、最后核验日期、本版本最重要的变化。
3. 正确做法与决策阈值。
4. 两个以上具体局势或地图场景。
5. 常见失败、对手反制和调整方法。
6. 来源与下一步阅读。

### 4. 不伪造视觉证据

没有真实可核验截图时，使用数据表、HTML/CSS 原生解释图、路线示意或决策图。不得生成看似真实的游戏画面来证明出生点、地形或操作行为。

### 5. 多语发布允许分批，但事实必须一致

- 英文是事实母稿和主要搜索入口。
- 中文是重点编辑版本，优先保证直接答案、术语和搜索意图自然。
- 紧急正式版本摘要允许先发布 en + zh；fr/de/nl 在事实稳定后分批补齐。
- 目标窗口：正式 Release 后 24 小时内完成 en + zh 玩家影响摘要，72 小时内完成受影响页面和其余语言。
- 数字、默认键位、版本范围和结论不允许因分批发布而漂移；`content-loop.md` 必须记录每个语种的状态。

### 6. 执行单位是内容批次，不是单页或单 PR

- 每次运行围绕一个主要玩家结果组织工作，但可以同时承接多个计划 ID、多个页面和多个独立交付物。
- 证据成熟时，默认完成“来源包 → 主答案或新页面 → 相邻旧页同步 → 多语 → 内链 → 验证”的完整链路，不在只改标题、日期或一小段后提前结束。
- 不设置“每次只能做一个任务、写一篇文章或创建一个 PR”的人为上限。只要仍有无冲突、已通过硬门槛的工作，就继续推进。
- 同一次运行可以创建多个 PR。每个 PR 应是一个可独立验证和合并的主题单元；互相依赖的 PR 必须写清基线、顺序和合并条件。
- 自动化自己创建或继续维护的 PR 在完整验证、同步最新 `main`、确认远端 head SHA 一致且 GitHub 判定可合并后直接 squash merge，不再等待人工审阅；任一门禁不满足时保留 PR 并明确报告阻塞。
- PR 数量和新增页面数仍不是 KPI。禁止用多个空 PR、薄页或重复意图伪造吞吐量。

### 7. 预发布信息必须显示生命周期

- `What's New` 可以使用公开 Issues 和 PRs 提前解释高价值玩家变化，但必须区分 `Released`、`Merged`、`In development` 和 `Watching`。
- 只有非 TEST 正式 Release 和对应 tag 能证明能力已经上线；`main` 提交或已合并 PR 不能写成当前正式能力。
- 开放 PR 的最终数值、交互和版本都可能变化。公开摘要只写稳定的玩家结果，不承诺发布日期。
- 安全 / 滥用、私有仓库、未批准提案、DevOps 和纯重构只进入内部账本，默认不公开。
- 同一玩家结果涉及多个 PR 时合并成一个主题；不按提交数量制造新闻流。

## 内容架构与完成定义

### 新鲜度层

这一层负责建立“始终最新”的第一印象：

- 首页优先展示“最新版本变化”“第一次玩”“快捷键”“经济增长”，原始数字降为辅助入口。
- `/whats-new/` 负责展示近期已上线、高价值已合并和少量开发中变化；它必须在首屏解释状态，并链接完整 changelog，而不是替代正式版本归档。
- 版本系列可以维护总览，也可以按独立玩家影响拆出小版本或专题页；页面数量不设硬上限。
- 受影响的常青攻略正文顶部统一显示：适用版本、最后核验日期、本版本最重要的变化。
- 页面更新不是只改 `updatedDate`；必须说明哪条玩家决策发生了变化。

完成标准：访客无需翻到来源面板或页脚，就能判断答案是否适用于当前版本；看到预发布条目时，也能判断它是已合并、开发中还是仅观察。

### 核心决策层

按真实需求和玩家价值排序：

1. 人口增长与部队甜区：何时停止扩张、保留多少兵、何时存钱。
2. 攻击比例：不同局势投多少兵，为什么兵多反而会输。
3. 快捷键与控制：速查页找键，教程页教连续操作和实战恢复。
4. Water Nukes：定义、触发、进攻、防守和常见误解全部在正文直接回答。
5. Doomsday Clock：宽限期、收圈节奏、部队/战舰衰减和撤退决策。
6. 出生点与边界形状：海岸、半岛、中心和瓶颈的具体判断。
7. 私人房设置：联盟时长、匿名名称、随机出生、Doomsday 等设置适合什么玩法。

完成标准：每篇只服务一个主要决策，并能从首页、相关机制页或相邻攻略获得至少两个自然入口。

### 地图试点层

不批量生成几十篇模板页。先验证五张差异明显的地图：Caribbean、Danish Straits、Venice、Yellow Sea、World Inverted。

每篇必须回答：

1. 更适合海战还是陆战。
2. 好出生点具有什么特征。
3. 最容易犯什么错误。
4. 哪些模式最好玩。
5. 中后期胜负通常在哪里决定。

完成标准：必须使用地图数据、可核验布局或解释图体现该地图的独特决策；若删掉地图名后文章仍可套到任何地图，则不发布。

## 每次运行如何组成内容批次

### 硬门槛

候选任务在进入本次执行批次前必须同时满足：

1. 有明确玩家问题和唯一主落地页。
2. 有足够的正式 Release、上游源码、生成数据或真实玩家反馈作为证据。
3. 能说明为什么更新现有页仍不够，才允许新建页面。
4. 能推进当前战役，或是不依赖未完成前置、与当前战役无冲突且证据成熟的并行项；事实错误 / 正式 Release 可以打断全部批次顺序。
5. 有可验证的完成定义，而不是“增加字数”或“多做一页”。

### 批次组成与停止条件

通过硬门槛后，不只选择一个候选，而是组合本次执行批次：

1. 一个锚点交付：推进当前战役，或处理事实错误 / 正式 Release。
2. 若干配套交付：相邻旧页同步、多语、内链、来源面板、内容完整性测试和入口更新。
3. 若干独立扩展：来源成熟且无前置阻塞的 Next/Later 主答案、新页面或地图试点。
4. 一个 PR 只承载一个清晰主题；不同主题、不同风险或可独立合并的工作拆成多个 PR。

没有固定的任务数、页面数或 PR 数上限。只有在剩余候选证据不足、会产生重复意图、依赖未合并前置、发生文件冲突、无法完成必要验证，或明确达到本次资源边界时，才结束运行。一个 PR 已经就绪，不是停止继续执行其他独立任务的理由。

证据充足时，优先把批次做成以下深度之一：

- 一个新主答案，加上多个相邻旧页、入口、多语和内容完整性测试的整组更新。
- 两个或更多互不争夺意图的新主答案，各自拥有来源包、自然入口和独立 PR。
- 一个版本总览，加上所有受影响机制、快捷键、攻略和语言状态的完整响应。
- 两张地图试点页及其对比入口，而不是只完成一张后立即停止。

这些是深度方向，不是机械配额；若事实和需求不足，仍应停止薄页，但不能把“避免数量 KPI”误解为“每次只做最小改动”。

### 优先判断

通过硬门槛后，用以下维度辅助判断，不按总分自动执行：

- 新鲜度风险：当前答案是否会让玩家做错决定。
- 玩家影响：问题影响多少局、影响是否直接。
- 已有需求：GSC、Feedlog、Issues 或社区是否反复出现。
- 复利价值：是否同时改善首页、内链、多个相邻页面或后续主题。
- 证据成熟度：事实是否稳定，是否适合立即本地化。
- 维护成本：是否会制造长期同步负担或薄页。

每次记录必须说明“本批次为什么选择这些项”“其他高价值候选为什么仍等待”，并写清它们之间的依赖和 PR 拆分。评分只能帮助编辑判断，不能替代判断。

### 合格的批次产出

定时运行不等于机械发文，但证据成熟时应尽可能完成可交付的内容集。合格产出包括：

- 完成多个独立主答案，或一个主答案及其完整受影响页面集。
- 成组新增玩家问题页或地图试点，并为每篇建立独立意图、来源、入口和验证。
- 为当前周目标建立可复用的来源包和决策大纲。
- 合并重复意图、修复入口或停止一个证据不足的选题。
- 核验发布后数据并决定继续、重写、合并或取消。

若某项没有足够证据或前置 PR 尚未合并，只暂停该项；其他独立、成熟的候选仍应继续。只有整个候选集都被阻塞或证据不足时，才只更新研究结论而不创建内容 PR。

## 可持续内容循环

### 每日：`What's New` 来源扫描

- 分别保存最新正式 Release 与上游 `main` 锚点；分叉历史不得解释成线性的“版本后新增提交”。
- 增量检查新合并 PR、更新过的高价值开放 PR、已批准 Issue，以及全部已跟踪条目的状态转换。
- 先执行玩家价值、安全和公开来源门槛，再决定 `publish`、`monitor`、`evergreen-only` 或 `suppress`。
- 没有实质状态或玩家结果变化时只更新执行结论，不刷新公共条目日期、不创建空 PR。
- 具体字段、状态迁移、首批候选和验证门禁见 [`whats-new-content-plan.md`](../whats-new-content-plan.md)。

### 正式版本发布

- 24 小时内：确认 Release 正文不是 TEST，占用 `FRESH-01` 通道，发布简短的 en + zh 玩家影响摘要；若五语可在不延误的情况下完成，可以一次发布。
- 72 小时内：更新被影响的机制、快捷键和攻略页；补齐 fr/de/nl；在页面顶部写清版本与关键变化。
- 不要求每个小修复都新建文章，也不禁止有独立玩家价值的小版本单独成页；改变玩家决策的内容可以进入系列总览、独立影响页或常青页。

### 每周

- 设定一个“玩家结果”，例如“玩家能判断何时停止扩张”，而不是“发布 population-growth 页面”。
- 围绕该玩家结果组织一个或多个内容批次，可以交付多篇互不重复的新玩家问题页、地图试点，以及相关旧页、入口和多语同步；不再设置每周最多一篇的上限。
- 周末检查当前战役的退出条件，必要时调整 Next/Later，但不因一天的新关键词随意打乱路线。

### 每月

- 查看 Search Console 7/28 天趋势、Feedlog 票数与评论、GitHub Issues 和页面反馈。
- 以搜索意图合并 query，记录错落地、低 CTR、内容缺口和已经解决的问题。
- 从真实问题中选择下月主题，并明确哪些候选被拒绝及原因。

### 每季度

- 清理过时版本描述、合并重复页面、重写低点击入口。
- 检查核心攻略的新鲜度摘要是否仍可信。
- 审核地图试点是否值得扩展；没有证据时停止，而不是补齐数量。

## Feedlog 作为选题池

Feedlog 不只是“提建议”入口。玩家可围绕以下问题提交和投票：

- 我为什么输了？
- 这个按钮或设置是什么意思？
- 哪张地图不会玩？
- 哪条攻略已经过时或没有直接回答问题？

每周将真实帖子规范化为玩家问题，合并重复项，记录票数、评论数、受影响页面和当前状态。系统欢迎帖、无内容占位和无法复现的问题不进入选题池。

候选进入计划时，`content-loop.md` 记录 Feedlog 帖子链接和票数；内容发布后回链权威页面，并把帖子状态更新为已解答或需要继续验证。票数是需求证据之一，不是唯一排序算法。

## 明确不做

- 不追求每个单位、建筑和地图都有一篇薄页面。
- 不批量写开发者、源码或部署教程；除非 GSC 或玩家反馈证明有稳定玩家需求。
- 不追逐拼错的品牌词。
- 不把每个小修复变成独立版本文章。
- 不把 GitHub 活动流、PR 标题列表或 Issue backlog 原样发布成 `What's New`。
- 不把 `Merged`、`In development` 或 `Watching` 写成已上线，也不引用私有 / 不可见仓库作为公开证据。
- 不用总页面数、字数或“连续发布天数”作为增长指标。
- 不因为五语未能同日完成而延迟紧急 en + zh 版本事实；也不允许长期遗忘待补语言。
- 不为了填满每日任务而发布证据不足、与现有页面重复或无法维护的内容。

## 计划变更规则

以下情况可以立即调整或打断当前战役：用户明确改变执行口径、已确认事实错误、有真实正文的正式 Release、会让玩家按旧结论操作失败的上游变化。

其他变化只在每周校准或每月复盘时调整本文。调整时必须写明新证据、被推迟的计划项和新的退出条件；每日账本不能自行把临时发现升级为长期战略。
